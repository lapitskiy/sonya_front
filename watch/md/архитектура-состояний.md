# Архитектура состояний SONYA-WATCH

Памятка, как дальше править прошивку часов, чтобы одна фича не ломала другую.

Главное правило: **модуль владеет своим состоянием сам**. Остальные модули только читают публичные функции или отправляют событие/команду через понятный интерфейс. Не надо снова раскидывать `sonya_ble_is_connected()`, флаги записи, READY и auto-off по разным местам.

## Владельцы состояния

### `link_state`

Владелец состояния связи с телефоном.

Состояния:

```text
DISCONNECTED  // BLE не подключен
CONNECTED     // GATT есть, но протокол еще не подтвержден
PROTO_READY   // был PING/PONG, приложение реально живое
```

Пишет:

- sync-мост из BLE-драйвера
- обработчик `PING` / `TIME`

Читают:

- `button_policy`
- `power_mgr`
- `status_ui` / `status_screen`
- запись и отправка событий

Правило: новые места **не должны** напрямую вызывать `sonya_ble_is_connected()`. Если нужно понять, есть ли связь, читать `link_state_is_connected()` или `link_state_get()`.

### `button_policy`

Владелец решения, что делать с физической кнопкой.

Вход:

- источник wake: кнопка или команда
- `link_state`
- идет ли запись

Выход:

```text
RECORD
IGNORE_NO_LINK
IGNORE_RECORDING
```

Правило: кнопка не должна сама включать экран, выключать питание или лезть в BLE. Она только решает: можно начинать запись или нет. Реальное выполнение записи делает `rec_flow` / `app_main`-dispatch.

### `power_mgr`

Владелец сна и авто-выключения.

Правила:

- не выключать, если идет запись
- не держать часы включенными только из-за `link_state`: сама BLE-связь, `BLE ADV` или GATT connect не считаются активностью
- сбрасывать таймер на реальные действия: `BLE_RX`, кнопку, wake
- не сбрасывать таймер на один только `BLE_CONNECT` / `BLE_DISCONNECT`, иначе автопереподключение телефона может бесконечно держать часы включенными
- через `AUTO_POWER_OFF_IDLE_MS` выключать, если нет реальной активности и не идет запись
- не делать PMU power-off при живом `VBUS/USB`: питание от провода может оставить экран на последнем кадре (`SONYA`/`OFF`) и выглядит как зависание.
- USB Serial/JTAG флаги липкие, поэтому перед проверкой нужно очищать их и ждать свежий SOF/USB-трафик. Старый флаг после выдёргивания кабеля не должен держать часы включенными.
- `USB_POWER` и ошибка PMU не являются активностью: они только откладывают повторную попытку выключения, не сбрасывая 30-секундный idle-таймер.

Правило: все проверки auto-off должны жить здесь. Не добавлять новые `if (... power off ...)` в экран, кнопку или BLE.

### `watch_idle_off`

Единственная точка, которая превращает idle timeout в физическое выключение.

Правила:

- `watch_idle_off_tick()` вызывается периодической задачей
- читает `power_mgr_auto_off_due()`
- проверяет живой USB/VBUS
- останавливает аудио через callback
- вызывает `watch_power_enter_auto_off()`
- при USB или ошибке PMU вызывает retry, а не `power_mgr_mark_activity()`

### `status_ui` / `status_screen`

Владелец отображения.

Вход:

- `link_state`
- `recording`
- `error`
- `app_ready`
- `time_synced`
- временное сообщение

Правило: экран ничего не решает про BLE, запись и питание. Он только показывает снимок состояния. Если экрану нужно знать связь, он читает `link_state`, а не BLE-драйвер.

### `rec_flow`

Будущий владелец записи и отдачи данных.

Сейчас часть логики еще в `app_main.c`, но цель такая:

```text
rec_flow_start(source)
rec_flow_stop()
rec_flow_send_meta_if_link()
```

Правило: детали `audio_cap`, `rec_store`, `pull_stream`, `REC_START`, `REC_END` должны постепенно уехать сюда. Кнопка и BLE-команда не должны знать, как устроена запись внутри.

### `WatchBleAutoConnectPolicy` на телефоне

Владелец решения, как часто телефон ищет часы и сколько длится окно сканирования.

Правила:

- если часы показывают `BLE ADV`, телефон должен регулярно сканировать эфир, а не зависать на прямом connect по старому BLE-кэшу
- прямое подключение по сохраненному адресу нельзя делать главным путем автоконнекта
- `SonyaWatchBleClient` выполняет scan/connect/write, но не должен сам хранить расписание reconnect
- `SonyaWatchViewModel` только включает/выключает auto-connect и показывает состояние пользователю

### `app_main.c`

Это не мозг системы, а проводка.

Что должно остаться:

- init модулей
- регистрация callbacks
- главный цикл dispatch
- вызовы `*_tick()` / `*_on_event()`

Что не должно расти обратно:

- собственные флаги BLE
- собственная логика кнопки
- собственная логика экрана
- собственная логика auto-off
- копии условий вида "если BLE, если READY, если запись"

## Как создавать новые связи

Перед новой правкой сначала ответить:

1. Кто владелец состояния?
2. Кто только читатель?
3. Это событие или запрос текущего состояния?
4. Что должно произойти при disconnect?
5. Что должно произойти при записи?
6. Что должно произойти при auto-off?

Если модуль хочет что-то узнать:

```text
OK:  link_state_is_connected()
BAD: sonya_ble_is_connected() из произвольного файла
```

Если модуль хочет что-то показать:

```text
OK:  status_ui_set_recording(true)
BAD: прямой вызов render_* из кнопки или BLE
```

Если модуль хочет записывать звук:

```text
OK:  rec_flow_start(...)
BAD: кнопка напрямую дергает audio_cap + rec_store + pull_stream
```

## Разрешенные направления зависимостей

```text
app_main
  -> link_state
  -> power_mgr
  -> button_policy
  -> status_ui
  -> rec_flow/audio_cap/rec_store/pull_stream
  -> sonya_ble

status_ui/status_screen
  -> link_state

button_policy
  -> link_state state values only

power_mgr
  -> link_state state values only

sonya_ble
  -> protocol / diaglog
```

Запрещенное направление:

```text
status_screen -> sonya_ble
button_policy -> sonya_ble
power_mgr -> sonya_ble
wake -> status_screen
sonya_ble -> status_screen
```

## Чеклист после каждой правки

Проверять всегда одно и то же:

```text
boot -> BLE advertising
phone connect -> link_state CONNECTED
PING -> link_state PROTO_READY
TIME -> READY + время
button while connected -> REC_START -> REC_END bytes=... -> meta send
button without BLE -> ignore_no_link, без записи
disconnect -> READY сброшен, ADV виден
30 sec without BLE -> AUTO_OFF
connected BLE >30 sec -> не выключается
```

## Как двигаться дальше

Порядок безопасного рефакторинга:

1. Закрепить `link_state` как единственный источник BLE-состояния.
2. Перенести всю кнопку из `app_main.c` в `button_policy` + отдельный executor.
3. Создать `rec_flow` и унести туда запись/commit/meta.
4. Создать `screen_ctrl`, который получает snapshot и дергает `status_ui`.
5. Оставить в `app_main.c` только init и dispatch.

После каждого шага: собрать, прошить, проверить чеклист выше.
